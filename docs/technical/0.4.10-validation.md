# 0.4.10 — prepare the booking transport before the burst

## Changes

- Preserve scheduled booking's five-second early start, 100 in-flight requests, 10 ms slot refill, and five-minute limit. Add now remains single-request.
- Prepare login, AWS verification token, and API connection before dispatch; final preparation normally begins 20 seconds before the configured opening. Cached preparation is required during the opening's first 30 seconds. If preparation has expired or the page changed, report the problem rather than silently performing token acquisition on the timing-critical path.
- Probe direct browser fetch with the legitimate `x-aws-waf-token` on a read-only cart request. Use it when the response is a valid cart. If unsupported, choose the SDK during preparation. Never duplicate a POST across transports, fall back on a 429, or remove server-side verification.
- Cache the in-page request dispatcher during preparation rather than compiling its full source on every burst request.
- When a 429 has no usable Retry-After, cool that request's slot for 1–2 seconds, matching the original per-request policy instead of imposing a new two-second global pause. An explicit Retry-After still pauses refills globally. No scheduled five-transient-failure cutoff.
- Observe Chromium's network send/completion events for booking POSTs. Logs show network dispatch relative to the burst target, measured network concurrency, response duration, and limited WAF/retry metadata. This is client-side network timing, not proof of when ReserveAmerica's server receives a request. No credentials, bodies, or full headers are logged.
- Add `npm run release:mac`, which refuses to produce the distribution ZIP unless signing, stapled notarization, and Gatekeeper checks pass on both the built app and fresh ZIP extraction.

## Installed live scheduled burst

Cowans Gap site 003, May 25–27, 2027, using the installed UI and available inventory. Final preparation took 1,185 ms and selected direct browser transport. The worker launched 4,997 ms before the configured opening. Chromium recorded the first network send 4,964.806 ms early, 100 sends over 118.186 ms, and 100 peak in-flight requests. One HTTP 417 arrived before the successful HTTP 200; the worker correctly waited for remaining responses and confirmed success after 300 ms. It navigated to the cart, which contained exactly one matching stay. Request count remained 100 after completion. Terminal network counters are snapshots at success, before cancellation drains remaining responses.

Both Pennsylvania test items were removed through the website without payment; the app was reset to idle. This validates dispatch and successful cart handoff against available inventory, not winning a genuine competitive release.

During scheduled-test cleanup, the website temporarily redirected to `/explore/error-405`; the cart still held the test item. A read-only production preparation call refreshed the session, obtained the legitimate verification token, and returned a valid HTTP 200 cart; reloading the normal cart page then recovered. This shows that the burst does not eliminate downstream website verification errors. No alternate endpoint, payment, or verification bypass was used.
