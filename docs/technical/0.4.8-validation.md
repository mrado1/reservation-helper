# Reservation Helper 0.4.8 — connection and booking repair

## Confirmed cause

On October 13, 2026, the embedded Reserve America website signed in successfully while the old helper's standalone Node cart GET returned HTTP 405. Both original auth cookies were present. The same endpoint returned HTTP 200 when requested by the current website, whose client refreshes authentication through `/refreshAuth` and uses the site's AWS WAF browser integration. The old helper incorrectly displayed all connection failures as invalid login credentials.

The helper now makes cart requests inside the signed-in Reserve America webview using that page's existing AWS integration. It refreshes the authenticated session using the site's current refresh flow. If the site requires verification, the helper stops and asks the user to complete it in the browser. It does not attempt to solve CAPTCHA or bypass verification.

The packaged-app smoke test also exposed deferred script execution while the main document was still loading. The transport and context reader now target `webContents.mainFrame.executeJavaScript` directly, with independent deadlines and cancellation, so unrelated page resources cannot hold up a request.

An additional live failure was caused by advertisement iframe navigation: the main process mistook those URLs for the selected campsite and cleared the selection. Context extraction now verifies the main page URL and ignores subframe navigation.

## Behavior

- **Add now:** validate connection, check for an existing exact cart item, submit the add-item request, verify the facility, site, arrival date and number of nights, and open the cart for required details and checkout.
- **Schedule:** selected by default. Users must explicitly enter and confirm the opening date/time and timezone; no release time is assumed. NY selections link to the official rules. Recommend setting up 3–5 minutes before opening, with attempts starting at the exact opening time.
- Scheduling is read-only before opening; it no longer sends a mutating preflight POST. The main process owns the schedule, refreshes the session every five minutes while waiting, and prepares it near opening. A renderer reload does not cancel the run.
- The app prevents idle app suspension while active. Keep the computer plugged in, connected, with its lid open and the app running. Closing the app cancels the schedule; schedules do not resume after quitting/restarting the app.
- At opening, the first POST starts immediately. Requests are serialized to avoid duplicate cart mutations. Expected early-opening responses retry at a 100 ms cadence after each response for up to 30 seconds. Rate limiting pauses the entire worker and respects Retry-After. Transient failures have bounded retries; unrecoverable input/auth/verification errors stop immediately.
- The run has an independent five-minute deadline. Stopping aborts pending requests and isolates old responses from subsequent runs. A request already processed by the server cannot be undone by aborting, so check the cart after stopping an in-flight request.
- Success requires an exact cart match, not a higher item count. The checkout handoff may require equipment/occupant details before payment; the helper does not fill or submit those details.
- Raw authentication credentials and customer/cart responses are not sent to the helper renderer or logs. Build packaging excludes the local private config and generates a public-only analytics configuration.

Instructions recommend setting up 3–5 minutes before release and staying at the computer to finish checkout. Trip dates are visually separate, and user-edited arrival/nights survive navigation between campsite pages.
