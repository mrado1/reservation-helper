# 0.4.9 — restore scheduled booking bursts

0.4.8 unintentionally replaced the earlier scheduled booking strategy with serial requests at the entered opening time. That was a functional regression for the user's release-window workflow, independent of the authentication repair.

Scheduled bookings now start five seconds before the user-entered opening time, maintain up to 100 in-flight add-to-cart requests, and refill available slots on a 10 ms main-process timer. Slow responses do not block other requests. Session preparation happens before the burst. Transient failures do not trigger 0.4.8's five-failure cutoff or exponential delay in scheduled mode; an explicit server rate limit still pauses refills according to Retry-After (two seconds when absent). The five-minute overall limit remains.

The repaired browser-session authentication and cart API endpoint are unchanged. Add now retains its existing single-request flow. Cart reconciliation is shared and runs separately from scheduled POST dispatch. Inventory/validation responses stop new dispatches but allow already-sent responses to confirm success before reporting failure. Success and cancellation abort remaining work; stale replies cannot affect another run.

Logs now include request count, in-flight count, and first dispatch relative to the early-start target. The booking UI tells the user requests start five seconds before their entered release time.

## Verification

- All 46 automated tests passed. New cases cover 100 overlapping slow requests, 10 ms slot refill, the exact early-start boundary, cancellation, stale responses, success racing inventory errors, rate-limit pauses, transient retries independent of cart checks, and the overall timeout.
- `npm run test:browser` runs the production worker and API client through actual Electron 30.5.1 Chromium frame execution. An isolated session intercepts all HTTPS requests and substitutes delayed API responses; it uses dummy credentials and a fetch-compatible SDK stub. No requests reach ReserveAmerica.
- Browser test: peak concurrency **100**, first request **4,985 ms before opening**, first 100 requests dispatched across **31 ms**, **1,000 total requests**, one auth refresh, confirmed success **1,132 ms after simulated opening** with 600 ms simulated responses. No additional POSTs after success.

This verifies scheduler and browser-bridge concurrency under simulated latency. It does not establish real ReserveAmerica latency, the live verification SDK's behavior under load, or success against competitors at a real release. The previous live available-inventory test is not evidence for competitive release performance.
